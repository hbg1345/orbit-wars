# 엔진 정합성 수정 및 검증 (2026-06-17)

## 배경

`physics.py` / `forecast.py` / `features.py`는 Kaggle `orbit_wars` 환경의 게임
엔진을 **재구현**한 것이다. 실제 엔진 원본은 다음 경로에 있다 (`kaggle-environments==1.30.1`):

```
kaggle_environments/envs/orbit_wars/orbit_wars.py
```

이 재구현이 엔진과 정확히 일치하는지 한 틱씩 대조 검증하고, 발견된 불일치를
수정했다. 검증 방식은 **두 에이전트가 step T부터 발사를 멈춰** forecast의
"no new launches" 가정과 동일한 조건을 만든 뒤, `forecast.simulate(obs_T, H)`의
예측을 엔진의 실제 미래 상태(`step T+1 … T+H`)와 비교하는 것이다.

검증 스크립트:
- `verify_forecast_multi.py` — forecast 롤아웃(소유주/함선/위치) vs 엔진
- `verify_aim.py` — 조준 각도가 실제로 타겟에 최소 턴에 명중하는지 vs 엔진
- `verify_features.py` — temporal 피쳐 인코딩이 forecast 원본으로 역디코딩되는지

## 수정 내역

### 1. 함대 속도 클램프 (`physics.fleet_speed`)

엔진은 속도를 `min(speed, max_speed)`로 제한하지만 재구현에는 클램프가 없었다.
1000척 초과 함대가 6을 넘는 속도로 계산되어 ETA가 어긋났다.

```python
speed = 1.0 + (MAX_SPEED - 1.0) * (log(max(ships,1)) / log(1000)) ** 1.5
return min(speed, MAX_SPEED)   # 추가
```

### 2. 출발 행성 영구 제외 제거 (`forecast._fleet_eta`)

재구현은 `bid == src`인 출발 행성을 충돌 대상에서 **영원히** 제외했다. 그러나
엔진은 출발 행성을 제외하지 않는다(함대를 `radius + 0.1` 바깥에 생성해 첫 충돌만
회피). 그 결과 **공전하는 출발 행성이 회전해 자기가 쏜 함대를 다시 쓸어담는**
경우, 엔진은 같은 소유주 증원으로 처리하지만 재구현은 그 함대를 무시해 함선을
과소 집계했다. → `src` 제외 로직 완전 제거.

### 3. 충돌 타이브레이크: 최소 거리 → 순서상 첫 충돌 (`forecast._fleet_eta`)

같은 틱에 여러 행성과 충돌할 때, 엔진은 `obs.planets` 리스트 순서상 **첫 번째**
행성을 고른다(`break`). 재구현은 최소 거리 행성을 골랐다. `at(k)`가 `obs.planets`
순서를 보존하므로, 최소 거리 대신 **순서상 첫 충돌**을 반환하도록 변경.

### 4. 조준 spawn 오프셋 일치 + 엔진 충돌 검증 (`physics.aim`)

- **spawn 오프셋**: 엔진은 함대를 `src_r + 0.1` 바깥에 생성하지만 aim은
  `src_r`(거리모델) / `src_r + 0.01`(생성점)을 썼다. `SPAWN_GAP = 0.1` 상수로
  통일.
- **`path_blocked` → `trace_fleet` 교체**: 기존 `path_blocked`는 자체 충돌 모델로
  경로 차단만 검사했다. 이를 엔진과 동일한 swept 연속 충돌 추적기
  `trace_fleet`(=`forecast._fleet_eta`와 동일 물리)로 교체. aim은 후보 각도를
  trace_fleet로 검증해 **실제로 의도한 타겟에 먼저 도달할 때만** 각도를 반환한다.
  이로써 경로 차단 검사와 정확한 도착 턴이 동시에 보장된다.

### 참고: turn 0 위상 퀴크 (수정 안 함)

reset(step 0) 관측은 행성 위치가 엔진 스텝핑과 한 틱 어긋나 있다
(`engine(k) = predict(k-1)`). step 1부터는 정확히 일치한다. 실제 에이전트는
게임 중 라이브 관측에서 조준하므로 영향받는 것은 **게임 첫 턴 한 번뿐**이며,
대부분 행성 반경 안이라 영향이 미미해 별도 수정하지 않았다.

## 정확도 변화

### forecast 롤아웃 (`verify_forecast_multi.py`)

수정 1·2·3 적용. 비교 대상: 미래 행성의 소유주 / 함선 수 / 위치.

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| owner 일치 | 100% | **100%** |
| ships 일치 (±0.5) | ~99.0% | **100%** |
| position 일치 (±0.5) | 100% | **100%** |

(T=60/H=30, T=100/H=45 등에서 총 6만+ 셀 비교)

ships 불일치(수정 전 ~99%)는 전적으로 수정 2(출발 행성 복귀 증원 누락)에서
발생했다. 단계별 실험:
- 출발 행성 영구 제외(원래): **99.21%**
- k=1에서만 제외: **99.98%**
- 제외 완전 제거(엔진 동일): **100%**

### 조준 각도 (`verify_aim.py`)

수정 4 적용. 라이브(중반) 관측에서 444발 발사, 실제 엔진에 쏴서 측정.

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 타겟 명중 | 99.1% | **100%** |
| 예측 턴 정확 | 97.8% | **100%** |
| 공전(움직이는) 타겟 명중 | 100% | **100%** |
| 공전 타겟 턴 정확 | 98.8% | **100%** |
| 엉뚱한 행성 명중 | 0.9% | **0** |
| 완전 빗나감(태양/장외) | 0 | **0** |

> 주의: 수정 전 첫 측정에서 명중 93.3%가 나왔으나, 이는 테스트가 step 0(위상
> 퀴크 구간)에서 조준한 결함이었다. 실제 플레이 조건(중반 관측)에서 다시 재면
> 수정 전이 99.1%였다. 위 표는 동일한 라이브 조건 기준의 수정 전/후 비교다.

### 피쳐 인코딩 (`verify_features.py`)

수정 사항 없음(원래부터 정확). `features.extract`의 temporal 블록을 forecast
원본으로 역디코딩해 검증.

| 게임 | 검사 셀 | 불일치 |
|---|---|---|
| 2인 | 45,120 | **0** |
| 4인 (enemy_1/2/3 전부 사용) | 31,200 | **0** |

확인 항목: owner one-hot(CCW 사분면 재키잉 포함), 함선 로그 스케일
(`expm1(ch·log1000)`), 위치 회전/정규화(`rot_k`).

## 검증된 범위와 전제

**검증된 것**: forecast가 계산하는 미래 상태의 물리, 그것을 네트워크 입력으로
넣는 인코딩, 그리고 조준 각도 — 모두 엔진과 일치함.

**전제 (설계상 의도, "오류" 아님)**:
- forecast는 **"지금 이후 새 함대 발사 없음"** 베이스라인이다. 이미 떠 있는
  함대의 착륙 + 생산까지만 정확하며, 실제 게임 미래의 예측은 아니다(상대가
  발사하는 순간 갈라짐). 네트워크는 이 기준선을 입력 신호로 학습한다.
- **미래 혜성 스폰은 모른다.** 혜성 생성은 에이전트에게 숨겨진 에피소드 시드로
  결정되기 때문이다(`orbit_wars.py`가 `configuration`에서 시드를 제거). 이미
  보드에 등장한 혜성의 미래 궤도는 정확히 예측한다.
